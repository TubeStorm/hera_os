## Mistakes already made once

- **[NEW - SLICE-1-OPENING-FAILURE-SEQUENCE, 2026-08-28]** Never pass `isolation: "worktree"` to the Agent tool in this repo. `AGENTS.md` rule 3 forbids secondary Git worktrees — the coordinator and all subagents must stay in the primary repo folder on `portfolio-week1`. Caught and cleaned up immediately (`git worktree remove`), no lasting damage, but it's an easy default to reach for by habit. Always launch builder/verifier/live-tester agents with no `isolation` param (or explicitly omit it).

- **[NEW - SLICE-1-OPENING-FAILURE-SEQUENCE, 2026-08-28]** A scroll-lock "mode" state machine (the `hardLockY` + `scroll`-listener-correction pattern used for `#video-section`'s locked gate, inherited from the old hero/lit gates) has a real re-trap failure mode: if the "re-enter the lock" check only tests "is the visitor currently at/past the threshold Y", then the very first scroll tick *away* from a just-unlocked boundary (visitor is still resting almost exactly at the threshold) re-satisfies that same test and immediately re-locks them — they can never leave. Fix: track `lastScrollY` and only re-arm the lock on an actual **crossing** (`lastScrollY` was short of the threshold **and** the new position has reached it), not merely "currently past it". If you touch or copy this locking pattern again, check for this specifically — it will not show up from a code read, only from actually trying to scroll back out of the locked section twice in a row.

- **[NEW - SLICE-1-OPENING-FAILURE-SEQUENCE, 2026-08-28]** In this session, the Claude Browser pane's `computer` `scroll` action and `javascript_tool` mutations (`window.scrollTo`, `element.style.opacity = ...`, even a `!important` stylesheet rule inserted via `insertRule`) were **unreliable** — sometimes a scroll gesture moved the page hundreds of pixels, sometimes an identical call produced zero movement, and `getComputedStyle(el).opacity` returned stale/wrong fractional values that didn't match the actual rendered page (confirmed by screenshot) or respond to a forced `!important` override. Read-only introspection (`element.matches(selector)`, `dataset` reads, attribute reads, and reading plain closure variables exposed via a temporary `Object.defineProperty(window, '__dbg', {get(){...}})` hook) was reliable and is what actually resolved the scroll-lock bug above — screenshots and `matches()`/attribute reads are trustworthy in this environment, but do not trust `getComputedStyle()` numeric output or assume a single `scroll`/`scrollTo` call actually moved the page without a screenshot or state-based check to confirm it. This matches `BROWSER-TESTING-PROTOCOL.md`'s framing (a broken transport is a tooling problem, not a product defect) — worth knowing before you spend an hour like this session did.

- **[NEW - BUG-002/BUG-003 repair, 2026-08-28 (repair builder)]** **Inline `style="left:...;top:..."` always beats a `@media` class/attribute-selector override — this is a real trap in this codebase, not just theory.** `OpeningFailureSequence.astro`'s mobile `@media (max-width:640px)` block had `.md-file[data-file='N']{left:...;top:...}` rules that looked correct but were **completely inert**: the elements' inline `style` attribute (built from the desktop-authored `files`/`thoughts` arrays in frontmatter) has higher specificity than any stylesheet selector without `!important`, so mobile was silently rendering desktop's raw coordinates the whole time. This is invisible from a code read — the media query looks right, the `display:none` hiding rules in the same block DID work (no conflicting inline `display`), so only the position rules were dead. Only caught by actually querying `getBoundingClientRect()` in the browser and cross-checking against the desktop array values. **If you need per-item authored positions/sizes that differ across breakpoints and the values are set inline per-item (common for staggered/animated layouts), use a CSS custom property in the inline style (`style="--x:...; --y:..."`) and have the base rule consume it (`left:var(--x)`), so a later stylesheet rule (media query or otherwise) can actually win the cascade.** Same fix pattern applies to `--r` (rotation) etc. if that ever needs a breakpoint override — it didn't this time, left as-is.
- **[NEW - BUG-002 repair, 2026-08-28 (repair builder)]** Don't assume a visually-wrong `hidden sm:inline` element is the bug just because the visible text matches its content — check computed style first. In this repair, the actual "HERA OS" text wrapping in the mobile nav pill was a **different, unrelated element**: `nav[0]` in `src/data/site.ts` (`{ label: 'HERA OS', href: '' }`, a real nav destination pointing home, redundant with the brand-mark link) — not the brand-mark's `hidden sm:inline` span, which was already correctly `display:none`. Also found in the same investigation: a flex child with an explicit Tailwind size class (`h-7 w-7`) can still be **flex-shrunk below that size** when its flex container (`justify-between`, no wrap) runs out of room and the child has no `shrink-0` — the brand logo `<img>` was rendering as an ~8px sliver on mobile for exactly this reason, easy to mistake for a broken/missing image at a glance.
