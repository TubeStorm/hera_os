- **[NEW - SLICE-1-OPENING-FAILURE-SEQUENCE, 2026-08-28]** A scroll-lock "mode" state machine (the `hardLockY` + `scroll`-listener-correction pattern used for `#video-section`'s locked gate, inherited from the old hero/lit gates) has a real re-trap failure mode: if the "re-enter the lock" check only tests "is the visitor currently at/past the threshold Y", then the very first scroll tick *away* from a just-unlocked boundary (visitor is still resting almost exactly at the threshold) re-satisfies that same test and immediately re-locks them — they can never leave. Fix: track `lastScrollY` and only re-arm the lock on an actual **crossing** (`lastScrollY` was short of the threshold **and** the new position has reached it), not merely "currently past it". If you touch or copy this locking pattern again, check for this specifically — it will not show up from a code read, only from actually trying to scroll back out of the locked section twice in a row.

- **[NEW - SLICE-1-OPENING-FAILURE-SEQUENCE, 2026-08-28]** In this session, the Claude Browser pane's `computer` `scroll` action and `javascript_tool` mutations (`window.scrollTo`, `element.style.opacity = ...`, even a `!important` stylesheet rule inserted via `insertRule`) were **unreliable** — sometimes a scroll gesture moved the page hundreds of pixels, sometimes an identical call produced zero movement, and `getComputedStyle(el).opacity` returned stale/wrong fractional values that didn't match the actual rendered page (confirmed by screenshot) or respond to a forced `!important` override. - **[NEW - BUG-002/BUG-003 repair, 2026-08-28 (repair builder)]** **Inline `style="left:...;top:..."` always beats a `@media` class/attribute-selector override — this is a real trap in this codebase, not just theory.** `OpeningFailureSequence.astro`'s mobile `@media (max-width:640px)` block had `.md-file[data-file='N']{left:...;top:...}` rules that looked correct but were **completely inert**: the elements' inline `style` attribute (built from the desktop-authored `files`/`thoughts` arrays in frontmatter) has higher specificity than any stylesheet selector without `!important`, so mobile was silently rendering desktop's raw coordinates the whole time. This is invisible from a code read — the media query looks right, the `display:none` hiding rules in the same block DID work (no conflicting inline `display`), so only the position rules were dead. Only caught by actually querying `getBoundingClientRect()` in the browser and cross-checking against the desktop array values. **If you need per-item authored positions/sizes that differ across breakpoints and the values are set inline per-item (common for staggered/animated layouts), use a CSS custom property in the inline style (`style="--x:...; --y:..."`) and have the base rule consume it (`left:var(--x)`), so a later stylesheet rule (media query or otherwise) can actually win the cascade.** Same fix pattern applies to `--r` (rotation) etc. if that ever needs a breakpoint override — it didn't this time, left as-is.

- **[NEW - SLICE-1-REPAIR, 2026-08-28 (builder)]** **`scroll-behavior: smooth` (`src/styles/global.css` line 41, global on `html`, dropped to `auto` only under `prefers-reduced-motion`) silently corrupts any Playwright/JS scroll-position test that reads `window.scrollY` right after a `window.scrollTo(0, y)` call.** The browser animates the scroll over real time, so a read even 200ms later can land mid-animation — e.g. a target of ~9960px read back as 377px. This looks exactly like a scroll-lock trap or a broken track height and cost real debugging time before the cause was found. Fix for any future scroll-position test in this repo: call `window.scrollTo({ top: y, left: 0, behavior: 'instant' })` explicitly (bypasses the CSS smooth-scroll), not the two-argument `scrollTo(0, y)` form, then a short `wait_for_timeout` is enough. This is a test-methodology fact, not a product defect — do not "fix" the global smooth-scroll CSS because of it.

- **[NEW - SLICE-1-FIX-2, 2026-08-29]** `html { scroll-behavior: smooth }` is set globally in `src/styles/global.css` (line ~41). Any Playwright checkpoint that uses `window.scrollTo(0, y)` therefore reads the page **mid-flight**, and every probe silently returns whatever frame the animation happened to be on. After a traversal finishes, the page is parked inside `#video-section` / `#loop-section`, whose gate handlers own the scroll position and fight any `scrollTo` back to the top — a second traversal in that page reports "everything skipped" and an upward-escape test reports "escape broken", both false. - **[NEW - SLICE-1-FIX-2, 2026-08-29]** A bounding-box coverage probe is NOT proof that a visual field reads as continuous. The `.md` curtain measured "0px horizontal gap across the full viewport width" while the rendered frame plainly showed scattered icons over open black — because the probe measured each column's box (full width, full stack height), not its ink. Screenshots caught what the numbers could not. Measure geometry *and* look at the frame; when they disagree, the frame wins.

- **[NEW - SLICE-1-FIX-2, 2026-08-29]** An Astro `<script>` **without** any attribute is processed and type-checked, so it can use TypeScript — but it is then subject to `npm run check` and will emit an error per untyped parameter and per `Element.style` access. Adding an attribute (e.g. `type="application/json"`) makes it `is:inline`, which skips both processing and type-checking. Passing config to a processed script via a `<script type="application/json">` data island + `JSON.parse` is cleaner than `define:vars` here: `define:vars` makes every injected name an unresolvable identifier to the checker (3 warnings in the previous build), whereas the data island plus proper type annotations leaves this component at 0 errors.
