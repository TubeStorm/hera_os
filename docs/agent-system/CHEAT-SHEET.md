- **[NEW - SLICE-1-OPENING-FAILURE-SEQUENCE, 2026-08-28]** A scroll-lock "mode" state machine (the `hardLockY` + `scroll`-listener-correction pattern used for `#video-section`'s locked gate, inherited from the old hero/lit gates) has a real re-trap failure mode: if the "re-enter the lock" check only tests "is the visitor currently at/past the threshold Y", then the very first scroll tick *away* from a just-unlocked boundary (visitor is still resting almost exactly at the threshold) re-satisfies that same test and immediately re-locks them — they can never leave. Fix: track `lastScrollY` and only re-arm the lock on an actual **crossing** (`lastScrollY` was short of the threshold **and** the new position has reached it), not merely "currently past it". If you touch or copy this locking pattern again, check for this specifically — it will not show up from a code read, only from actually trying to scroll back out of the locked section twice in a row.

- **[NEW - SLICE-1-OPENING-FAILURE-SEQUENCE, 2026-08-28]** In this session, the Claude Browser pane's `computer` `scroll` action and `javascript_tool` mutations (`window.scrollTo`, `element.style.opacity = ...`, even a `!important` stylesheet rule inserted via `insertRule`) were **unreliable** — sometimes a scroll gesture moved the page hundreds of pixels, sometimes an identical call produced zero movement, and `getComputedStyle(el).opacity` returned stale/wrong fractional values that didn't match the actual rendered page (confirmed by screenshot) or respond to a forced `!important` override. - **[NEW - BUG-002/BUG-003 repair, 2026-08-28 (repair builder)]** **Inline `style="left:...;top:..."` always beats a `@media` class/attribute-selector override — this is a real trap in this codebase, not just theory.** `OpeningFailureSequence.astro`'s mobile `@media (max-width:640px)` block had `.md-file[data-file='N']{left:...;top:...}` rules that looked correct but were **completely inert**: the elements' inline `style` attribute (built from the desktop-authored `files`/`thoughts` arrays in frontmatter) has higher specificity than any stylesheet selector without `!important`, so mobile was silently rendering desktop's raw coordinates the whole time. This is invisible from a code read — the media query looks right, the `display:none` hiding rules in the same block DID work (no conflicting inline `display`), so only the position rules were dead. Only caught by actually querying `getBoundingClientRect()` in the browser and cross-checking against the desktop array values. **If you need per-item authored positions/sizes that differ across breakpoints and the values are set inline per-item (common for staggered/animated layouts), use a CSS custom property in the inline style (`style="--x:...; --y:..."`) and have the base rule consume it (`left:var(--x)`), so a later stylesheet rule (media query or otherwise) can actually win the cascade.** Same fix pattern applies to `--r` (rotation) etc. if that ever needs a breakpoint override — it didn't this time, left as-is.
- **[NEW - BUG-002 repair, 2026-08-28 (repair builder)]** Don't assume a visually-wrong `hidden sm:inline` element is the bug just because the visible text matches its content — check computed style first. In this repair, the actual "HERA OS" text wrapping in the mobile nav pill was a **different, unrelated element**: `nav[0]` in `src/data/site.ts` (`{ label: 'HERA OS', href: '' }`, a real nav destination pointing home, redundant with the brand-mark link) — not the brand-mark's `hidden sm:inline` span, which was already correctly `display:none`. Also found in the same investigation: a flex child with an explicit Tailwind size class (`h-7 w-7`) can still be **flex-shrunk below that size** when its flex container (`justify-between`, no wrap) runs out of room and the child has no `shrink-0` — the brand logo `<img>` was rendering as an ~8px sliver on mobile for exactly this reason, easy to mistake for a broken/missing image at a glance.

- **[NEW - SLICE-1-REPAIR, 2026-08-28 (builder)]** **`scroll-behavior: smooth` (`src/styles/global.css` line 41, global on `html`, dropped to `auto` only under `prefers-reduced-motion`) silently corrupts any Playwright/JS scroll-position test that reads `window.scrollY` right after a `window.scrollTo(0, y)` call.** The browser animates the scroll over real time, so a read even 200ms later can land mid-animation — e.g. a target of ~9960px read back as 377px. This looks exactly like a scroll-lock trap or a broken track height and cost real debugging time before the cause was found. Fix for any future scroll-position test in this repo: call `window.scrollTo({ top: y, left: 0, behavior: 'instant' })` explicitly (bypasses the CSS smooth-scroll), not the two-argument `scrollTo(0, y)` form, then a short `wait_for_timeout` is enough. This is a test-methodology fact, not a product defect — do not "fix" the global smooth-scroll CSS because of it.
- **[NEW - SLICE-1-REPAIR, 2026-08-28 (builder)]** **A component's scoped `<style>` class does not reach into a different Astro component, even with an identical class name.** `OpeningFailureSequence.astro` referenced `.user-bubble-mini` (defined in `src/pages/index.astro`'s own scoped `<style>` block, ~line 426) expecting to inherit that look; Astro scopes each file's styles with its own `data-astro-cid-*` hash, so the rule compiles to `.user-bubble-mind[data-astro-cid-index-xxx]` and never matches elements rendered by the child component. The bubble silently rendered as plain unstyled text — invisible from a source read, only caught by an actual screenshot. If a packet says "reuse this class from another component," re-author the same declaration block inside the component that needs it (or promote the rule to a shared global stylesheet) — do not assume cross-component class reuse works by name alone.
- **[NEW - SLICE-1-REPAIR, 2026-08-28 (builder)]** **`@media (prefers-reduced-motion: reduce)` overrides that force `opacity: 1 !important` on an element unconditionally (not scoped to a `[data-scene='...']` selector) will show that element in every discrete scene, not just the one it belongs to.** Caught via Playwright screenshot: an unconditional `.rw { opacity: 1 !important; }` meant to make the AI response readable without a fade transition was instead showing the full response text during the `composer` and `sent` reduced-motion states too, collapsing the intended discrete story into one frame. Always gate a reduced-motion "make this fully visible" override behind the same `data-scene` (or equivalent) selector used for the layer's own show/hide logic, not a bare tag/class selector.

- **[NEW - SLICE-1-REPAIR round 2, 2026-08-28 (builder)]** **A `.md`-rain-style density effect needs its per-column travel duration decoupled from the scene's own end boundary, or every column is forced to finish at the same instant and the "peak" collapses to almost no scroll distance.** All 14 rain columns previously shared one endpoint (`P.answerEnd`, a locked scene boundary) as the denominator of their local progress fraction, so a column activating later than another had less time to transit — different speeds, same finish line. Measuring peak density empirically (grid-sampling what fraction of the AI-response bounding box is covered by rain-file rects, not eyeballing it) showed the true peak was under 55% coverage and lasted only ~0.02 of scroll. Decoupling to a fixed `RAIN_TRAVEL_DURATION` constant independent of the scene table (the shared opacity fade at `clear1Start/clear1End` still owns when it actually disappears, so nothing leaks past the fade) plus compressing the column activation stagger into a tighter band raised peak coverage to **~84% at p≈0.50**, sustained above 55% for roughly 0.10 of scroll. Measure density with a canvas/grid-coverage script, not by eye — "looks pretty dense" and "84% of the text's bounding box is physically covered" are very different bars.
